# 13 · App 对接说明书（协议 + 流程 + 操作）

> 交付对象：App 开发
> 版本基线：主控 M v1.83（`0xDB2742BD`）· 蓝牙板 S v1.16（`0x9AA0FB65`）
> 固件日期：2026-11-21
> 本文所有字节序、超时、错误码均来自当前固件实测，不是推测。

---

## 0. 先搞清楚谁是谁

| 角色 | 芯片 | 职责 | App 能不能直接对话 |
|---|---|---|---|
| **M 主控** | GD32F303CB | 测距、推荐杆算法、杆包表存储、电源管理。Modbus 从站 `0x01` | ❌ 不能。M 没有 BLE |
| **S 蓝牙板** | N32WB031 | BLE 外设，App 的唯一入口；把 App 的请求转成 Modbus/UART 发给 M | ✅ **只有 S 有 BLE** |

**App 只跟 S 说话。** M 的一切能力（版本、杆包表、推荐杆）都要经 S 转发。

两条互不相干的通道，用不同的帧头区分：

| 通道 | 帧头 | 用途 |
|---|---|---|
| **应用通道** | `53 A2`（下行）/ `54 A1`、`53 A2`（上行） | 日常业务：版本、测距数据、杆包表 |
| **升级通道** | `EB 90` | 固件 OTA（进 boot 后走这条） |

## 1. BLE 连接

### 1.1 广播与 UUID

| 项 | 值 |
|---|---|
| 设备名 | `AIMTECH VHR` |
| 名字前缀（扫描过滤用） | `AIMTECH`（备用 `J51NG`） |
| Service UUID | `00002760-08c2-11e1-9073-0e8ac72e1001` |
| Write Characteristic | `00002760-08c2-11e1-9073-0e8ac72e0001` |
| Notify Characteristic | `00002760-08c2-11e1-9073-0e8ac72e0002` |

### 1.2 连接步骤（照这个顺序做，别省）

```
1) 扫描：按 namePrefix 过滤（不要扫全部再筛）
2) connect
3) getPrimaryService(SERVICE)
4) getCharacteristic(WRITE) / (NOTIFY)
5) ⚠️ 必须先 setCharacteristicNotification + 写 CCCD 使能通知
6) 请求 MTU 247（Android: requestMtu(247)）
7) 此时才能发第一条命令
```

**第 5 步是必须的**：不订阅通知，S 的所有应答你都收不到，表现为"发出去没反应"（这坑我们踩过）。

### 1.3 写方式

| 阶段 | 支持 |
|---|---|
| APP 模式（日常） | **只支持 write-without-response** |
| Boot 模式（升级中） | write 与 write-without-response 都支持 |

> 用 write-with-response 在 APP 模式下会超时失败。**一律用 write-without-response。**

### 1.4 权限（Android 12+）

- `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT`
- 6.0~11 还需要 **定位权限** 且 **打开系统定位开关**，否则扫不到任何设备
- iOS：需要 `NSBluetoothAlwaysUsageDescription`

## 2. 应用通道帧格式

### 2.1 下行（App → S）

```
+------+------+--------+--------+------+-----------+--------+--------+
| 0x53 | 0xA2 | len_lo | len_hi | cmd  | payload…  | sum_lo | sum_hi |
+------+------+--------+--------+------+-----------+--------+--------+
                len = payload 字节数 + 3
                sum = (0x53 + 0xA2 + len_lo + len_hi + cmd + payload 各字节) & 0xFFFF
```

### 2.2 上行（S → App）

**两种帧头都要收**，格式与下行同构：

| 帧头 | 含义 |
|---|---|
| `54 A1` | S 主动上报（测距结果、电量、状态） |
| `53 A2` | 对 App 命令的应答（`0x0F`/`0x15`/`0x21`/`0x22` 等） |

> ⚠️ 很多现成的 BLE 解析只认一种帧头。**两种都必须解析**，否则"命令有应答但收不到"。

### 2.3 参考实现（流式解析 + 组帧）

```text
// ---- 组帧 ----
fun buildFrame(cmd: Byte, payload: ByteArray): ByteArray {
    val len = payload.size + 3
    val f = ByteArray(7 + payload.size)
    f[0]=0x53; f[1]=0xA2.toByte()
    f[2]=len and 0xFF; f[3]=(len shr 8) and 0xFF
    f[4]=cmd
    payload.copyInto(f, 5)
    var sum = 0
    for (i in 0 until 5 + payload.size) sum += f[i].toInt() and 0xFF
    f[5+payload.size]= (sum and 0xFF)
    f[6+payload.size]= ((sum shr 8) and 0xFF)
    return f
}

// ---- 流式解析：通知可能拆包/并包，必须缓存再按 len 切 ----
val buf = ArrayDeque<Byte>()

fun onNotify(chunk: ByteArray) {
    buf.addAll(chunk.toList())
    while (buf.size >= 4) {
        val h0 = buf[0].toInt() and 0xFF
        val h1 = buf[1].toInt() and 0xFF
        if ((h0 != 0x53 && h0 != 0x54) || h1 != 0xA1 && h1 != 0xA2) {
            buf.removeFirst(); continue          // 找帧头
        }
        val len = (buf[2].toInt() and 0xFF) or ((buf[3].toInt() and 0xFF) shl 8)
        if (len < 3 || len > 512) { buf.removeFirst(); continue }
        val total = 4 + len
        if (buf.size < total) return             // 半帧，等下一包
        val f = buf.toList().subList(0, total)
        var sum = 0
        for (i in 0 until total - 2) sum += f[i].toInt() and 0xFF
        val got = (f[total-2].toInt() and 0xFF) or ((f[total-1].toInt() and 0xFF) shl 8)
        buf.subList(0, total).clear()
        if (sum != got) continue                 // 校验错，丢掉
        val cmd = f[4].toInt() and 0xFF
        val payload = f.subList(5, total - 2).toByteArray()
        dispatch(cmd, payload)
    }
}
```

### 2.4 分包与 MTU

- MTU 协商到 247 → 单帧有效载荷上限 **244 B**，建议单帧 ≤ **228 B**
- 大于这个长度自己拆（本项目现有命令最大 68+4 B，不会超）
- 通知可能**被拆成多包到达**，解析器必须做**流式拼包**（按 len 字段）

## 3. 命令速查表

### 3.1 下行命令

| cmd | 名称 | payload | 应答 |
|---|---|---|---|
| `0x03` | 雷达休眠/唤醒（预留，当前无实际动作） | `01` 唤醒 / `02` 休眠 | 无 |
| `0x04` | 设置当前杆号 | `club(1) num(1)` | 无 |
| `0x0A` | 查构建号 | 空 | `0x13`（4 B 日期码） |
| `0x0D` | 杆包表分片写入 | `off_lo off_hi n data[n]`（n ≤ 28） | `0x15`，ack=`0x01` |
| `0x0E` | 杆包表命令 | `01` 提交 / `02` 恢复默认 / `03` 擦除 / `04` 查状态 | 需再发 `0x0F` 取结果 |
| `0x0F` | 取杆包表结果 | 空 | `0x15`（6 B） |
| `0x20` | 查板卡描述 | `id`：`1`=S蓝牙板 `2`=M主控 | `0x21`（12 B） |
| `0x21` | 查板卡型号 | `id` 同上 | `0x22`（13 B） |

### 3.2 主动上报（`54 A1`）

| cmd | 内容 | 长度 | 说明 |
|---|---|---|---|
| `0x03` | 球速 | 8 B | 原生字节，暂未定标 |
| `0x06` | 电量 | 1 B | `0`~`4` 格 |
| `0x07` | 距离 / 两点距 | 2 B **小端** | 单位 **分米（dm）**，`/10` 得米 |
| `0x08` | 坡度 | 2 B 小端 | dm |
| `0x09` | 垂直高差 | 2 B 小端 | dm |
| `0x0A` | 推荐杆 | 2 B 小端 | 杆号，见 3.4 |
| `0x0B` | 雷达开关状态 | 1 B | |
| `0x0C` | 测量模式 | 1 B | `0`=单点 `1`=两点 |
| `0x13` | 版本 | 4 B | 见 3.3 |

### 3.3 版本帧 `0x13` / 板卡描述 `0x21` / 型号 `0x22`

```
0x13 (4B):  uint32 小端「构建号」，形如 2026081401（YYYYMMDDnn）
0x21 (12B): id(1) stage(1) fw_major(1) fw_minor(1) crc32(4,LE) size(4,LE)
            stage: 0 = 运行在 APP，1 = 运行在 BOOT
0x22 (13B): id(1) model(12, ASCII，如 "N2SE_S")
```

> ⚠️ **`0x13` 是构建日期码，不是固件版本**。界面上要显示的 `v1.16` 这种版本号，
> 必须从 `0x20` → `0x21` 的 `fw_major/fw_minor` 取。
> `0x20`/`0x21` 也是判断"设备当前在跑 APP 还是 BOOT"的唯一方式，**升级前后都应各查一次**做对比。

|---|---|---|---|---|---|
| `0x00` | W1 | `0x06` | H5 | `0x0C` | I7 |
| `0x01` | W3 | `0x07` | H6 | `0x0D` | I8 |
| `0x02` | W5 | `0x08` | I3 | `0x0E` | I9 |
| `0x03` | W7 | `0x09` | I4 | `0x0F` | PW |
| `0x04` | H3 | `0x0A` | I5 | `0x10` | GW |
| `0x05` | H4 | `0x0B` | I6 | `0x11` | SW |
| `0x12` | LW | `0x13` | AW | `0x14` | Pt |
| `0xEF` | 无推荐 | | | | |

## 4. 流程 A：连接后读设备信息

```
连接成功
  → 0x0A                → 收 0x13：S 的构建号（日期码，不是 vX.YY）
  → 0x20 [0x01]         → 收 0x21：S 的描述（含 crc32 / size / stage）
  → 0x20 [0x02]         → 收 0x21：M 的描述
  → 0x21 [0x01] / [0x02]→ 收 0x22：型号字符串
```

界面显示建议：`S v1.16 / M v1.83`、`当前模式 APP/BOOT`、`CRC`。

> 若 `0x20 [0x02]` 一直拿不到 → 说明 S 还没和 M 握上手（M 未上电或串口没通），此时应提示"主控未就绪"，而不是"设备异常"。

## 5. 流程 B：测距数据订阅

订阅通知后，S 会不定时推 `54 A1`。App 只需要被动接收 + 解析，不用轮询。

```
0x07 距离      → 主显（÷10，单位米）
0x0C 模式      → 决定 0x07 是"单点距离"还是"两点距"
0x0A 推荐杆    → 推荐杆图标/文字
0x06 电量      → 电量格
```

## 6. 流程 C：自定义杆包（第 5 档 Pro）

### 6.1 表结构（68 字节）

```
偏移  长度  内容
0x00   1    'G' (0x47)
0x01   1    'R' (0x52)
0x02   1    版本 = 1
0x03   1    杆数 = 13
0x04   1    容差 = 5
0x05   1    保留 0
0x06   2    CRC16（小端，见下）
0x08   8    保留，填 0xFF
0x10  52    13 根 × { mean(int16 LE), sigma(uint16 LE) }
```

- 单位是**码 ×2**（定长整数）：`mean = (最近 + 最远)`，`sigma = (最远 - 最近) / 2`
- 整表先填 `0xFF`，再写上述字段
- **CRC16-CCITT**：init `0xFFFF`，poly `0x1021`，对**整 68 字节**计算，计算前把 `[6][7]` 置 0，结果回填到 `[6][7]`（小端）

> 主控会用同样的算法重算并和管理值比对，**不一致直接拒收**。所以 CRC 必须由 App 正确填写。

### 6.2 下发时序（必须按这个顺序）

```
① 0x0D  off=0x0000 n=28  + 表[0..27]      → 等 0x15 ack=0x01（回显 off/n）
② 0x0D  off=0x001C n=28  + 表[28..55]     → 等 0x15 ack=0x01
③ 0x0D  off=0x0038 n=12  + 表[56..67]     → 等 0x15 ack=0x01
④ 0x0E  [0x01]                             （提交）
⑤ 0x0F 轮询 → 0x15 ack=0x02（提交完成）
```

- 每帧之间**间隔 400~500 ms**（S 要转成 Modbus 写给 M）
- ④ 之后**不要立刻发 ⑤**，建议 200 ms 后再开始轮询，轮询间隔 200 ms，总超时 **8 s**
- 提交成功后，**主控会自动切到第 5 档「自定义 Pro」**，App 不需要再发切档命令

### 6.3 读当前状态

```
0x0E [0x04]  → 200 ms 后 0x0F 轮询 → 0x15 ack=0x04
```

界面拿 `本地 CRC` 和 `主控 CRC` 比对：

| 情况 | 显示 |
|---|---|
| `valid=0` | 主控：无自定义表 → 需要下发 |
| `crc` 相等 | ✅ 已是最新 |
| `crc` 不等 | ⚠️ 需要更新 |

### 6.4 擦除

```
0x0E [0x03] → 0x0F 轮询 → 0x15 ack=0x03
```
擦除后主控自动从第 5 档退回第 1 档。

### 6.5 `0x15` 应答格式（6 字节）

```
ack(1) valid(1) ver(1) count(1) crc_lo(1) crc_hi(1)
```

| ack | 含义 | App 处理 |
|---|---|---|
| `0x01` | 分片已收到 | 继续发下一片 |
| `0x81` | 命令已受理，处理中 | **不算结束**，继续轮询 |
| `0x02` | 提交完成 | 读 valid/count/crc 判结果 |
| `0x03` | 擦除完成 | |
| `0x04` | 状态查询结果 | |
| `0x91` | 主控链路未就绪（S 刚上电/升级中） | 提示"稍后重试" |
| `0x92` `0x93` `0x94` | 第 1/2/3 片下发被拒（串口没发出去） | 重发该片 |
| `0xE1` | 主控 600 ms 内没应答 | 可再点一次（内部已重试一次） |
| `0xE2` | S 侧串口这一帧没发出去 | 重试 |
| `0x82`~`0x8F` | 主控 Modbus 异常（`0x80` \| 异常码） | 显示错误码 |

## 7. 流程 D：OTA 升级

### 7.1 什么时候用

- 升级**主控 M**：只更新 M 的 APP 区
- 升级**蓝牙板 S**：只更新 S 的 APP 区
- ⚠️ **boot 区不通过 OTA 更新**，必须 SWD 烧录（现场升级碰不到）

### 7.2 进入 Boot

APP 模式下发一帧即可（S 会自动转给 M / 自己进 boot）：

```
53 A2 04 00 FF 01 F9 01
```

随后设备复位进 boot，**BLE 会断开**，等 1~2 s 重新扫描连接（boot 广播名不变）。

### 7.3 升级帧（`EB 90`）

```
EB 90 | type(2, BE) | len(2, BE) | payload | CRC8
CRC8 = CRC-8/MAXIM（poly 0x07, init 0），校验范围 = type + len + payload
```

| type | 方向 | 名称 | payload |
|---|---|---|---|
| `0x0000` | S→App | 心跳 | 空 |
| `0x0101` | App→S | 握手 | 16 B 硬件码 + 补 0xFF |
| `0x0102` | S→App | 握手应答 | status + hw(16) + version(4) + maxpkt(2,BE @21) |
| `0x0201` | App→S | 参数 | size(4,BE) + SHA256(32) + pkt(2,BE) = 38 B |
| `0x0202` | S→App | 参数应答 | status(1) |
| `0x0301` | App→S | 数据 | seq(2) + total(2) + len(2) + data |
| `0x0302` | S→App | ACK | status + seq(2) |
| `0x0303` | S→App | NACK | status + seq(2)（从该 seq 重发） |
| `0x0401` | App→S | 校验 | 32 B SHA |
| `0x0402` | S→App | 校验应答 | status + 32 B 实算摘要 |
| `0x0501` | App→S | 完成 | 空（APPLYING 期间要重发） |
| `0x0502` | S→App | 完成应答 | status：`0x00` 成功 / `0xFF` 失败 |

**Status 码**：`0x00` OK / `0x11` SHA 失败 / `0x21` 序号错 / `0x22` 长度错 / `0x23` Flash 错 / `0xFF` 应用超时

### 7.4 完整时序

```
进 Boot（AB 帧）→ 重连
  → 0x0101 握手（等 0x0102，超时 3 s）
  → 0x0201 参数（size + SHA256 + pkt；等 0x0202，超时 3 s）
  → 0x0301 循环发数据，每包等 0x0302；收到 0x0303 从该 seq 重发
  → 0x0401 校验（等 0x0402，比对 32 字节）
  → 0x0501 完成（等 0x0502；没回应就每 500 ms 重发，最多 20 次）
  → 设备重启进 APP → 断开 → 重连 → 用 0x20 查版本确认
```

### 7.5 分包建议（实测参数）

| 参数 | 值 |
|---|---|
| 单包数据 | **128 B** |
| 窗口 | 8 包 |
| 包间隔 | 4 ms |
| MTU | 247 |

实测：S 板 360 包 ≈ 4 s，M 主控 755 包 ≈ 12 s。

### 7.6 一键升级顺序（重要）

```
1) 升主控 M  → 完成后重连、确认版本
2) 升蓝牙板 S → 它是最后一步：S 一升级，BLE 立刻断，必须重新扫描连接
```

**顺序不能反**，也不能同时升。

## 8. 超时与重试（照抄即可）

| 动作 | 超时 | 重试 |
|---|---|---|
| 扫描连接 | 8 s | 3 次，每次重新扫描 |
| `0x0D` 分片 | 1 s | 重发该片 2 次 |
| `0x0E` 提交 + 轮询 | 8 s | 1 次 |
| `0x0E` 读状态 + 轮询 | 4 s | 1 次 |
| 升级握手/参数 | 3 s | 2 次 |
| 升级数据包 | 2 s | 3 次（按 NACK seq 重发） |
| 升级完成 | 10 s | 20 次 × 500 ms |

`0x0F` 轮询间隔 **200 ms**（别更密，S 内部一次完整读要 0.3~1.3 s）。

## 9. 已知限制（App 必须处理）

| 限制 | 表现 | App 要做的事 |
|---|---|---|
| **同一时刻只有一条 BLE 链路** | 别人连着时你扫不到设备 | 提示"设备已被其他设备连接" |
| **连接期间设备停止广播** | 第二次扫描扫不到 | 连接前先断开旧链路 |
| **5 分钟无按键 → 关蓝牙 → 8 s → 关机** | 放着不动就断线，且再也连不上 | 断线提示"设备已休眠，请按键唤醒" |
| **升级与杆包下发互斥** | 同时做会把表写坏（主控已加 CRC 校验会拒收） | UI 上互斥：升级中禁用杆包按钮 |
| **S 升级后立刻断连** | 升完必须重新扫描 | 升级完成后自动重连 |
| **`0xE1` 主控无应答** | 偶发，多发在刚上电/刚写完 flash | 自动重试一次，仍失败再报错 |
| **iOS 无 Web Bluetooth** | 网页版在 iOS 用不了 | App 用原生 BLE，不受影响 |

### 10.1 首页 / 连接

| `0xE1` | 主控无应答：请重试 |

### 10.2 杆包页（自定义 Pro）

| 元素 | 行为 |
|---|---|
| 13 行输入 | 每行「最近 ~ 最远」，单位码；右侧实时算 `均值 ± σ` |
| 读取主控状态 | `0x0E[04]` + 轮询 → 显示 `主控：v1 13 杆 crc=0xXXXX` |
| 下发到主控 | 6.2 那五步 |
| 载入默认 | 本地填默认表，不动设备 |
| 擦除 | `0x0E[03]` |

状态栏固定三段：`本地 crc=0xXXXX　主控：…　→ 结论`

**给用户的提示**：这张表对应设备设置页的**第 5 档「自定义 Pro」**。下发成功后主控会**自动切到第 5 档**，不需要再去设备上手动切。

### 10.3 升级页

| 元素 | 行为 |
|---|---|
| 扫描设备 | 读 S/M 版本与 CRC（`0x20`） |
| 选择固件 | 本地 `.bin`，显示版本/大小/CRC |
| 开始升级 | 7.4 流程，显示进度条与包计数 |
| 中止 | 发 `0x0501` 失败即放弃，设备留在 boot，下次可重试 |

## 12. FAQ / 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 命令发出去无任何回帧 | 没订阅通知 / 写方式用了 write-with-response | 见 1.2 / 1.3 |
| 只能收到部分回帧 | 解析器只认 `54A1`，没认 `53A2` | 两种帧头都要解析 |
| 长帧解析乱码 | 没做流式拼包 | 按 len 累计再解析 |
| 扫描偶发扫不到 | 设备已被连接 / 已自动关机 | 先断开、按键唤醒 |
| 杆包提交老 `0xE1` | 主控忙或总线撞车 | 重试一次；仍失败看是否刚上电 |
| 升级卡在握手 | 设备还在 APP 没进 boot | 先发 `53 A2 04 00 FF 01 F9 01` |
| 升级后连不上 | S 正在重启广播 | 等 2 s 再扫 |
| 下发后设备档位变了 | 这是**设计行为**：提交成功自动切第 5 档 | 不需要额外处理 |
