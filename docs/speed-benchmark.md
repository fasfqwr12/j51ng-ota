## 瓶颈定位（埋点数据）

```
writes: 300~455
wrAvg:  4.5 ~ 5.0 ms     ← 单包写入很快，不是瓶颈
wrP50:  ~4 ms
wrP90:  ~7.5 ms
rounds: 20 ~ 33
ackAvg: 264 ~ 285 ms     ← 每轮 ACK 等待，才是瓶颈
```

设备每 8 包回一次 ACK，一次约 170~285 ms（期间在写闪存）。
窗口 8 → 45 轮 × 184 ms ≈ 8 s；窗口 32 → 20 轮 → 5.2 s。
**结论：加大发送窗口，把固定 ACK 开销摊薄到更多数据上。**

## 总耗时（含连接/复位重连）

| 场景 | 桌面版 | 网页版 |
|---|---|---|
| S（已在 Boot） | 16.33 s（含其自身重连） | **28.2 s**（含 4.5 s 连接），页面计时 25.4 s |
| M（已在 Boot） | 23.9 s | **32.2 s**，页面计时 32.2 s |

拆解（网页 S，2026-11-09 19:23）：

```
连接/识别       4.5 s
数据 300 包     5.6 s   ← 与桌面持平
SHA + 搬运      8 s     ← 设备侧
复位 + 重连     11 s    ← Windows Chrome 慢
```

结论：**数据阶段已追平**，总耗时差距来自「复位后 Chrome 重连」与「进 Boot」，
属于浏览器/系统层，不是协议或分包问题。

## 连接健壮性修正

- `gatt()` / `enterBoot()` 加单飞锁，避免并发重连互打断（`already in progress`）
- 写入遇 `no longer valid` / `disconnected` 自动重连并重发一次
- 连接失败主动 `gatt.disconnect()`，避免设备被占住不再广播
- 0x0501 前给设备 4 s 搬运时间，减少无效轮询（16 s → 8 s）


## 重连优化后的最终数据（2026-11-09 19:29-19:33，线上 v34）

| 场景 | 桌面版 | 网页版 | 说明 |
|---|---|---|---|
| S（Boot→完成） | 16.33 s | **14.2 s**（墙钟 16.1 s） | 数据 5.2 s，重连 1 次 1 s |
| M（Boot→完成） | 23.9 s | **20.8 s**（墙钟 22.1 s） | 数据 7.8 s，重连 1 次 1 s |

### 关键修复：重连前不要反复 disconnect

旧代码每次重连尝试都调用 `device.gatt.disconnect()`，把 Chrome 的连接状态机弄卡，
表现是 `GATT operation failed for unknown reason` 连续失败 3~4 次（约 11 s）。

改为「只连不踢」后：

```
[5] 设备已确认接管（0x0502=0x00）
19:29:43  重连成功（第 1 次尝试）      ← 1 秒
19:29:43  [6] 设备已重启，运行新 APP
```

实测扫描确认：设备广播几乎连续（每 3 s 出现、停 2 s 是扫描窗口造成），
浏览器侧不该等这么久，问题出在代码而不是设备。

### 进 Boot 的 17 s 是设备侧

从 APP 切 Boot 时，S 板要写标志→复位→Boot 重新初始化广播，实测约 17 s
（17:35:03→17:35:20、18:38:04→18:38:21、19:31:22→19:31:36 均一致）。
桌面版同样要付这个时间，只是它的预检在计时器之外，所以「总耗时」里看不到。
