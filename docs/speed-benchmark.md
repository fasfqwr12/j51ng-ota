设备：AIMTECH VHR（J51VA-S，MAC 4B:AC:00:15:39:33）
镜像：S = 68,224 B（300 包），M = 103,700 B（455 包），包长均为设备协商值 228 B。

## 瓶颈定位（埋点数据）

```
writes: 300~455
wrAvg:  4.5 ~ 5.0 ms     ← 单包写入很快，不是瓶颈
wrP50:  ~4 ms
wrP90:  ~7.5 ms
rounds: 20 ~ 33
ackAvg: 264 ~ 285 ms     ← 每轮 ACK 等待，才是瓶颈
```

设备每 8 包回一次 ACK，一次约 170~285 ms（期间在写闪存）。
窗口 8 → 45 轮 × 184 ms ≈ 8 s；窗口 32 → 20 轮 → 5.2 s。
**结论：加大发送窗口，把固定 ACK 开销摊薄到更多数据上。**

## 总耗时（含连接/复位重连）

| 场景 | 桌面版 | 网页版 |
|---|---|---|
| S（已在 Boot） | 16.33 s（含其自身重连） | **28.2 s**（含 4.5 s 连接），页面计时 25.4 s |
| M（已在 Boot） | 23.9 s | **32.2 s**，页面计时 32.2 s |

拆解（网页 S，2026-11-09 19:23）：

```
连接/识别       4.5 s
数据 300 包     5.6 s   ← 与桌面持平
SHA + 搬运      8 s     ← 设备侧
复位 + 重连     11 s    ← Windows Chrome 慢
```

结论：**数据阶段已追平**，总耗时差距来自「复位后 Chrome 重连」与「进 Boot」，
属于浏览器/系统层，不是协议或分包问题。

## 连接健壮性修正

- `gatt()` / `enterBoot()` 加单飞锁，避免并发重连互打断（`already in progress`）
- 写入遇 `no longer valid` / `disconnected` 自动重连并重发一次
- 连接失败主动 `gatt.disconnect()`，避免设备被占住不再广播
- 0x0501 前给设备 4 s 搬运时间，减少无效轮询（16 s → 8 s）
