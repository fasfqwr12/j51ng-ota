0. 先搞清楚谁是谁

角色芯片职责App 能不能直接对话
M 主控GD32F303CB测距、推荐杆算法、杆包表存储、电源管理。Modbus 从站 0x01❌ 不能。M 没有 BLE
S 蓝牙板N32WB031BLE 外设，App 的唯一入口；把 App 的请求转成 Modbus/UART 发给 M✅ 只有 S 有 BLE

App 只跟 S 说话。 M 的一切能力（版本、杆包表、推荐杆）都要经 S 转发。

两条互不相干的通道，用不同的帧头区分：

通道帧头用途

1. BLE 连接

1.1 广播与 UUID

1.2 连接步骤（照这个顺序做，别省）

1) 扫描：按 namePrefix 过滤（不要扫全部再筛）
2) connect
3) getPrimaryService(SERVICE)
4) getCharacteristic(WRITE) / (NOTIFY)
5) ⚠️ 必须先 setCharacteristicNotification + 写 CCCD 使能通知
6) 请求 MTU 247（Android: requestMtu(247)）
7) 此时才能发第一条命令

第 5 步是必须的：不订阅通知，S 的所有应答你都收不到，表现为"发出去没反应"（这坑我们踩过）。

1.3 写方式

阶段支持
APP 模式（日常）只支持 write-without-response
Boot 模式（升级中）write 与 write-without-response 都支持
用 write-with-response 在 APP 模式下会超时失败。一律用 write-without-response。

1.4 权限（Android 12+）

  • BLUETOOTH_SCAN / BLUETOOTH_CONNECT
  • 6.0~11 还需要 定位权限 且 打开系统定位开关，否则扫不到任何设备
  • iOS：需要 NSBluetoothAlwaysUsageDescription

2. 应用通道帧格式

2.1 下行（App → S）

+------+------+--------+--------+------+-----------+--------+--------+
| 0x53 | 0xA2 | len_lo | len_hi | cmd  | payload…  | sum_lo | sum_hi |
+------+------+--------+--------+------+-----------+--------+--------+
                len = payload 字节数 + 3
                sum = (0x53 + 0xA2 + len_lo + len_hi + cmd + payload 各字节) & 0xFFFF

2.2 上行（S → App）

两种帧头都要收，格式与下行同构：

帧头含义
54 A1S 主动上报（测距结果、电量、状态）
53 A2对 App 命令的应答（0x0F/0x15/0x21/0x22 等）
⚠️ 很多现成的 BLE 解析只认一种帧头。两种都必须解析，否则"命令有应答但收不到"。

2.3 参考实现（流式解析 + 组帧）

// ---- 组帧 ----
fun buildFrame(cmd: Byte, payload: ByteArray): ByteArray {
    val len = payload.size + 3
    val f = ByteArray(7 + payload.size)
    f[0]=0x53; f[1]=0xA2.toByte()
    f[2]=len and 0xFF; f[3]=(len shr 8) and 0xFF
    f[4]=cmd
    payload.copyInto(f, 5)
    var sum = 0
    for (i in 0 until 5 + payload.size) sum += f[i].toInt() and 0xFF
    f[5+payload.size]= (sum and 0xFF)
    f[6+payload.size]= ((sum shr 8) and 0xFF)
    return f
}

// ---- 流式解析：通知可能拆包/并包，必须缓存再按 len 切 ----
val buf = ArrayDeque<Byte>()

fun onNotify(chunk: ByteArray) {
    buf.addAll(chunk.toList())
    while (buf.size >= 4) {
        val h0 = buf[0].toInt() and 0xFF
        val h1 = buf[1].toInt() and 0xFF
        if ((h0 != 0x53 && h0 != 0x54) || h1 != 0xA1 && h1 != 0xA2) {
            buf.removeFirst(); continue          // 找帧头
        }
        val len = (buf[2].toInt() and 0xFF) or ((buf[3].toInt() and 0xFF) shl 8)
        if (len < 3 || len > 512) { buf.removeFirst(); continue }
        val total = 4 + len
        if (buf.size < total) return             // 半帧，等下一包
        val f = buf.toList().subList(0, total)
        var sum = 0
        for (i in 0 until total - 2) sum += f[i].toInt() and 0xFF
        val got = (f[total-2].toInt() and 0xFF) or ((f[total-1].toInt() and 0xFF) shl 8)
        buf.subList(0, total).clear()
        if (sum != got) continue                 // 校验错，丢掉
        val cmd = f[4].toInt() and 0xFF
        val payload = f.subList(5, total - 2).toByteArray()
        dispatch(cmd, payload)
    }
}

2.4 分包与 MTU

  • MTU 协商到 247 → 单帧有效载荷上限 244 B，建议单帧 ≤ 228 B
  • 大于这个长度自己拆（本项目现有命令最大 68+4 B，不会超）
  • 通知可能被拆成多包到达，解析器必须做流式拼包（按 len 字段）

3.3 版本帧 0x13 / 板卡描述 0x21 / 型号 0x22

0x13 (4B):  uint32 小端「构建号」，形如 2026081401（YYYYMMDDnn）
0x21 (12B): id(1) stage(1) fw_major(1) fw_minor(1) crc32(4,LE) size(4,LE)
            stage: 0 = 运行在 APP，1 = 运行在 BOOT
0x22 (13B): id(1) model(12, ASCII，如 "N2SE_S")
⚠️ 0x13 是构建日期码，不是固件版本。界面上要显示的 v1.16 这种版本号，
必须从 0x20 → 0x21 的 fw_major/fw_minor 取。
0x20/0x21 也是判断"设备当前在跑 APP 还是 BOOT"的唯一方式，升级前后都应各查一次做对比。

4. 流程 A：连接后读设备信息

连接成功
  → 0x0A                → 收 0x13：S 的构建号（日期码，不是 vX.YY）
  → 0x20 [0x01]         → 收 0x21：S 的描述（含 crc32 / size / stage）
  → 0x20 [0x02]         → 收 0x21：M 的描述
  → 0x21 [0x01] / [0x02]→ 收 0x22：型号字符串

界面显示建议：S v1.16 / M v1.83、当前模式 APP/BOOT、CRC。

若 0x20 [0x02] 一直拿不到 → 说明 S 还没和 M 握上手（M 未上电或串口没通），此时应提示"主控未就绪"，而不是"设备异常"。

5. 流程 B：测距数据订阅

订阅通知后，S 会不定时推 54 A1。App 只需要被动接收 + 解析，不用轮询。

0x07 距离      → 主显（÷10，单位米）
0x0C 模式      → 决定 0x07 是"单点距离"还是"两点距"
0x0A 推荐杆    → 推荐杆图标/文字
0x06 电量      → 电量格

6. 流程 C：自定义杆包（第 5 档 Pro）

6.1 表结构（68 字节）

偏移  长度  内容
0x00   1    'G' (0x47)
0x01   1    'R' (0x52)
0x02   1    版本 = 1
0x03   1    杆数 = 13
0x04   1    容差 = 5
0x05   1    保留 0
0x06   2    CRC16（小端，见下）
0x08   8    保留，填 0xFF
0x10  52    13 根 × { mean(int16 LE), sigma(uint16 LE) }
  • 单位是码 ×2（定长整数）：mean = (最近 + 最远)，sigma = (最远 - 最近) / 2
  • 整表先填 0xFF，再写上述字段
  • CRC16-CCITT：init 0xFFFF，poly 0x1021，对整 68 字节计算，计算前把 [6][7] 置 0，结果回填到 [6][7]（小端）
主控会用同样的算法重算并和管理值比对，不一致直接拒收。所以 CRC 必须由 App 正确填写。

6.2 下发时序（必须按这个顺序）

① 0x0D  off=0x0000 n=28  + 表[0..27]      → 等 0x15 ack=0x01（回显 off/n）
② 0x0D  off=0x001C n=28  + 表[28..55]     → 等 0x15 ack=0x01
③ 0x0D  off=0x0038 n=12  + 表[56..67]     → 等 0x15 ack=0x01
④ 0x0E  [0x01]                             （提交）
⑤ 0x0F 轮询 → 0x15 ack=0x02（提交完成）
  • 每帧之间间隔 400~500 ms（S 要转成 Modbus 写给 M）
  • ④ 之后不要立刻发 ⑤，建议 200 ms 后再开始轮询，轮询间隔 200 ms，总超时 8 s
  • 提交成功后，主控会自动切到第 5 档「自定义 Pro」，App 不需要再发切档命令

6.3 读当前状态

0x0E [0x04]  → 200 ms 后 0x0F 轮询 → 0x15 ack=0x04

界面拿 本地 CRC 和 主控 CRC 比对：

情况显示
valid=0主控：无自定义表 → 需要下发
crc 相等✅ 已是最新
crc 不等⚠️ 需要更新

6.4 擦除

0x0E [0x03] → 0x0F 轮询 → 0x15 ack=0x03

擦除后主控自动从第 5 档退回第 1 档。

6.5 0x15 应答格式（6 字节）

ack(1) valid(1) ver(1) count(1) crc_lo(1) crc_hi(1)
ack含义App 处理
0x01分片已收到继续发下一片
0x81命令已受理，处理中不算结束，继续轮询
0x02提交完成读 valid/count/crc 判结果
0x03擦除完成
0x04状态查询结果
0x91主控链路未就绪（S 刚上电/升级中）提示"稍后重试"
0x92 0x93 0x94第 1/2/3 片下发被拒（串口没发出去）重发该片
0xE1主控 600 ms 内没应答可再点一次（内部已重试一次）
0xE2S 侧串口这一帧没发出去重试
0x82~0x8F主控 Modbus 异常（0x80 \异常码）显示错误码

7. 流程 D：OTA 升级

7.1 什么时候用

  • 升级主控 M：只更新 M 的 APP 区
  • 升级蓝牙板 S：只更新 S 的 APP 区
  • ⚠️ boot 区不通过 OTA 更新，必须 SWD 烧录（现场升级碰不到）

7.2 进入 Boot

APP 模式下发一帧即可（S 会自动转给 M / 自己进 boot）：

53 A2 04 00 FF 01 F9 01

随后设备复位进 boot，BLE 会断开，等 1~2 s 重新扫描连接（boot 广播名不变）。

7.3 升级帧（EB 90）

EB 90 | type(2, BE) | len(2, BE) | payload | CRC8
CRC8 = CRC-8/MAXIM（poly 0x07, init 0），校验范围 = type + len + payload
type方向名称payload
0x0000S→App心跳空
0x0101App→S握手16 B 硬件码 + 补 0xFF
0x0102S→App握手应答status + hw(16) + version(4) + maxpkt(2,BE @21)
0x0201App→S参数size(4,BE) + SHA256(32) + pkt(2,BE) = 38 B
0x0202S→App参数应答status(1)
0x0301App→S数据seq(2) + total(2) + len(2) + data
0x0302S→AppACKstatus + seq(2)
0x0303S→AppNACKstatus + seq(2)（从该 seq 重发）
0x0401App→S校验32 B SHA
0x0402S→App校验应答status + 32 B 实算摘要
0x0501App→S完成空（APPLYING 期间要重发）
0x0502S→App完成应答status：0x00 成功 / 0xFF 失败

Status 码：0x00 OK / 0x11 SHA 失败 / 0x21 序号错 / 0x22 长度错 / 0x23 Flash 错 / 0xFF 应用超时

7.4 完整时序

进 Boot（AB 帧）→ 重连
  → 0x0101 握手（等 0x0102，超时 3 s）
  → 0x0201 参数（size + SHA256 + pkt；等 0x0202，超时 3 s）
  → 0x0301 循环发数据，每包等 0x0302；收到 0x0303 从该 seq 重发
  → 0x0401 校验（等 0x0402，比对 32 字节）
  → 0x0501 完成（等 0x0502；没回应就每 500 ms 重发，最多 20 次）
  → 设备重启进 APP → 断开 → 重连 → 用 0x20 查版本确认

7.5 分包建议（实测参数）

参数值
单包数据128 B

包间隔4 ms
MTU247

实测：S 板 360 包 ≈ 4 s，M 主控 755 包 ≈ 12 s。

7.6 一键升级顺序（重要）

1) 升主控 M  → 完成后重连、确认版本
2) 升蓝牙板 S → 它是最后一步：S 一升级，BLE 立刻断，必须重新扫描连接

顺序不能反，也不能同时升。

11. 自测清单（逐条打勾）

  • [ ] 扫描能发现 AIMTECH VHR，连接 < 2 s
  • [ ] 不订阅通知时命令无应答（确认订阅是必须的）
  • [ ] 0x0A 能读回 4 字节版本，与设备屏幕一致
  • [ ] 0x20[1] / 0x20[2] 都能返回 12 字节，stage 正确
  • [ ] 测距一枪，能收到 0x07 距离、0x0A 推荐杆
  • [ ] 杆包读状态返回 valid=1 count=13 crc=…
  • [ ] 杆包下发后 本地 crc == 主控 crc，且设备自动切第 5 档
  • [ ] 故意改坏一个字节再下发 → 主控拒收，CRC 不变（防写坏机制）
  • [ ] 升级主控：755 包左右，12 s 内完成，重启后版本变更
  • [ ] 升级蓝牙板：360 包左右，完成自动重连，版本变更
  • [ ] 升级中禁用杆包按钮（互斥）
  • [ ] 断开连接后重新扫描能再次发现设备

现象原因处理
命令发出去无任何回帧没订阅通知 / 写方式用了 write-with-response见 1.2 / 1.3
只能收到部分回帧解析器只认 54A1，没认 53A2两种帧头都要解析
长帧解析乱码没做流式拼包按 len 累计再解析
扫描偶发扫不到设备已被连接 / 已自动关机先断开、按键唤醒

  5. 杆包：0x0D×3 + 0x0E[1] + 0x0F 轮询 + 比对 CRC
