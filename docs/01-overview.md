# J51NG OTA 总览：谁在干什么

> 本文只描述**已验证的代码与实机行为**，不含推测。
> 冻结基线：2026-11-11。两个 boot 均已烧录，本轮文档**不修改任何固件**。

## 1. 三个角色

| 角色 | 芯片 | 职责 | 谁给它升级 |
|---|---|---|---|
| **上位机** | PC / 手机浏览器 | 选固件、算 SHA256、分包、发帧、收应答 | — |
| **S 蓝牙板** | N32WB031 | **BLE 从机 + 中转站**：收 BLE 包 → 写自己的暂存 flash → 校验 → 转发给主控 / 搬运到自己 APP 区 | 自己（目标 S），或被 SWD 烧 |
| **M 主控** | GD32F303CB | **UART 从机**：收 S 板发来的 0x10xx 帧 → 写自己 APP 区 → 算 SHA256 → 回报 | S 板转发（目标 M） |

**关键认知：上位机从来不直接和主控说话。** 所有 M 升级流量都要经过 S 板的中转。

## 2. 两条完全不同的升级路径

```
                    ┌── 目标 S：S 板自己升级
上位机 ──BLE──→ S板 ┤
                    └── 目标 M：S 板暂存后，经 UART 转发给主控
```

| | 目标 S | 目标 M |
|---|---|---|
| 固件落到哪 | S 板暂存区 `0x01030000` | 同样是 S 板暂存区 |
| 谁校验暂存区 | S 板自己 | S 板自己 |
| 下一步 | **搬运**：暂存区 → S 板 APP 区 `0x01010000` | **转发**：暂存区读出 → UART 0x1011 帧 → 主控 |
| 主控参与 | 完全不参与 | 全程参与 |
| 完成后谁复位 | S 板复位进新 APP | 主控跳新 APP；**S 板留在 boot 继续广播** |
| 上位机要重连吗 | 要（S 板断了） | 不要（链路保持） |

## 3. 分区（硬约束）

### M 主控 GD32F303CB，Flash 128 KB

| 区段 | 地址 | 大小 |
|---|---|---|
| M boot | `0x08000000–0x08001FFF` | 8 KB |
| M boot_data | `0x08002000–0x080027FF` | 2 KB |
| M APP | `0x08002800–0x0801BFFF` | 102 KB |
| 参数 / UI / SC5660 | `0x0801C000` 起 | 16 KB |

### S 蓝牙板 N32WB031，Flash 512 KB

| 区段 | 地址 | 大小 |
|---|---|---|
| S boot | `0x01000000`– | 64 KB 上限 |
| S boot_data | `0x0100FF00` | 256 B 页 |
| S APP | `0x01010000` | 128 KB |
| **暂存区** | `0x01030000` ~ Flash 末尾 | 镜像**先写这里**，两个目标共用 |

> 暂存区是整套设计的枢纽：**无论升级 M 还是 S，BLE 收到的包永远先写这里**。

## 4. 两个上位机（同一套协议，不同节奏）

| | 桌面插件 `ble_daemon.py` | 网页 `ota_web/src/app.js` |
|---|---|---|
| 传输 | Python bleak / WinRT | Chrome Web Bluetooth |
| 分包 | **128 B** × 816（M 镜像） | **228 B** × 458（设备 maxpkt） |
| 窗口 | win=32，每 4 包 sleep 4 ms | win=32，**每包 sleep 4 ms** |
| 连接 | 常驻守护进程，唯一 BLE 中心 | 浏览器页，唯一 BLE 中心 |
| 实机结果 | ✅ 成功过（job-0002：`0x1021 status=0` → `0x0502=0x00`） | ⚠️ 数据层全通，`0x0402=0x11` SHA 失败 |

**同一时刻只能有一个 BLE 中心。** 设备一旦被连上就不再广播，另一个工具会报「扫不到」。这不是守护进程占用 bug，是 BLE 协议本分。
