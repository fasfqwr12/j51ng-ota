M 实机结果✅ 成功过 0x1021 status=0 → 0x0502=0x00❌ 0x0402=0x11 SHA 失败
失败记录⚠️ 早前 status=17 / 参数无应答⚠️ 数据全 ACK 但暂存区内容不对
协议 / CRC / SHA完全一致，差异只有节奏
竞态根因：S 板 0x0202 在暂存区还没擦完时就发出，上位机立刻灌 458 包； 而 process() 擦除期间 return PENDING 不取 BLE 帧 → 数据帧堆在 RX 环里被丢， 批量 ACK 却照发 → 「全包 ACK、0 重传」但暂存区是旧数据 → 实算 SHA ≠ 期望值。 插件包更小更慢、且 UART idle hook 里额外跑 BLE process，所以更容易过，但不是零概率。
修复方向（已编译未烧）：把 0x0202 挂起到 erase done 之后再发； 擦除期间用 peek 只放行控制帧，数据帧留在环里不消费。主机收到应答才开始发数据，竞态从时序上消失。

一个中心原则BLE 协议设备连上任意中心后不再广播；插件 / 网页 / 手机同一时刻只能有一个
复位判据坑：只在 target==SUB 时复位，但 reset_session() 会先把 target 清掉 → 判断永远不成立 → 升级成功却不复位。正确做法：在置 reset_pending 时把目标存进独立 s_dispatch_target，main 用 getter 读它。
完成应答坑：APPLYING 期间 process() 提前 return，0x0501 连读都没读。 上位机必须重发（插件 2 s×30、网页 1.5 s×30），等 apply 结束回 BEACON 才被处理。
